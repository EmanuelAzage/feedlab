# FeedLab Update Log

## 2026-08-02

* **Update**: **M3 instrumentation wired end to end.** `PlaybackObserver` collapses KVO on the player, KVO on the layer and three item notifications into one vocabulary, stamping each event inside its own callback; `PlaybackEventPipe` serialises them; `SessionRecorder` folds each item view on release. First real numbers from live playback: `apple-bipbop-fmp4: ttff 356 ms, watch 5.40s, stalls 0, ratio 0.000, switches 3`. Switch counts of 2/0/3 across three streams confirm ABR detection is real rather than constant. 64 tests, lint clean.
* **Correction**: **Startup buffering was being counted as a stall.** `AVPlayer` waits `.toMinimizeStalls` while filling its buffer before the first frame, which satisfies the stall condition in [QoE metrics](qoe-metrics.md) as literally written — so **every item reported exactly one stall** of 0.4–0.65 s, double-counting startup as both time-to-first-frame and a rebuffer. A constant bias survives averaging and shifts every arm alike, so it would have read as a real finding rather than an error. Stalls now require playback to have begun; the same streams re-measure at zero. Definition and implementation updated together.
* **Decision**: **Ordered event delivery** ([decisions](decisions.md)). A `Task` per callback spawns unordered tasks, so an event stamped before `.itemReleased` could arrive after it and never be folded — correct timestamps, wrong record. Replaced with an unbounded `AsyncStream` drained by one detached consumer.
* **Update**: **M3 underway — the pure core is done.** `PlaybackEvent` vocabulary, `MetricsEngine` as a fold over recorded events, `PlaybackRecord`, and `SessionSummary` with nearest-rank p90. Suite is now **62 tests across 5 suites**, covering every case `testing.md` requires: clean playback, one long stall vs many short, user pause excluded from both numerator and denominator, zero-watch items excluded from ratios but counted as skipped, TTFF when `readyForDisplay` precedes or follows intent, and nil TTFF for an item that never rendered. Remaining in M3: `PlaybackObserver` (the AVFoundation side) and the playback gestures.
* **Update**: **The `Metrics/` purity guard exists.** FeedLab is a single module, so no compiler enforces the no-AVFoundation rule — a test now scans `Metrics/` for forbidden imports, fails loudly if the directory is missing (a guard that vacuously passes is worse than none), and includes a test of the matcher itself so it cannot silently stop detecting anything.
* **Decision**: Four entries in [decisions](decisions.md) — `PlaybackEvent` moved into `Metrics/` because it *is* the boundary and belongs inside the guarded region; **optional means "not applicable", never zero** (reporting zero bitrate switches for a progressive file would read as a flawless ABR result and, given a corpus of 7 HLS to 15 progressive, would dominate the mean); p90 specified as nearest-rank because the README quotes it and "p90" alone is not a specification; gestures assigned to M3 since user-pause events are a metrics-correctness requirement rather than a UI nicety.
* **Update**: **Portrait-lock documented as a deliberate non-goal** in [product spec](product-spec.md). It was previously only expressed in `project.yml`, so it read as accidental. The deciding reason is not convention but that rotation resizes the player layer and forces relayout mid-playback, which the run protocol cannot hold constant across arms.
* **Update**: **M2 complete.** First device session — iPhone 12 Pro, iOS 26.5.2. The app builds, signs, installs and runs in both `Measure` and `Debug`. A 36 s Time Profiler trace under continuous scrolling closes the last M2 criterion: **zero** hangs at the 250 ms threshold, ~422 ms of main-thread CPU across 36.4 s, and the only media symbols on main-thread stacks were notification delivery (~35 ms total). `-[AVURLAsset initWithURL:options:]` and `-[AVPlayerItem initWithAsset:]` are absent from main, confirming the `ItemPreparer` fix independently of the debug assert. Recorded as criterion-clearing evidence, **not** a README number: single run, no fixed scroll script, unthrottled. Practical device-session gotchas added to [testing](testing.md) — chiefly that profiling needs USB, since a wireless trace fails silently and produces a zero-duration trace targeting the *Mac*.
* **Correction**: **A departed item kept playing.** `cellDidEndDisplaying` skipped teardown when the index was still `currentIndex`, so during a long drag the previous video stayed audible over cells the user had already scrolled to — and kept accruing watch duration, which is the denominator of rebuffer ratio, so it would have quietly flattered the smoothness of any item scrolled away from. Now torn down unconditionally, with `currentIndex` cleared so settling back on it restarts playback. Found by the user on device, not by any test.
* **Correction**: **Asset and item construction were running on the main thread.** `FeedCoordinator` is `@MainActor`, and an unstructured `Task { }` inherits that isolation — so `AVURLAsset(url:)` and `AVPlayerItem(asset:)` ran on main despite living inside a task. Playback worked correctly the whole time, because `await` releases the actor while AVFoundation does its I/O elsewhere, which is precisely why simulator verification missed it; found by logging `Thread.isMainThread` before spending a device session on the Instruments check it would have failed. Fixed by moving the work into `ItemPreparer.prepare`, a `nonisolated async` method that runs on the global executor (SE-0338), with a debug `assert` guarding the invariant. See [decisions](decisions.md).
* **Update**: **M2 feature-complete** apart from the Instruments main-thread check, which needs a device and is carried into the M4 session rather than claimed from a simulator run. `FeedCell` owns a persistent `AVPlayerLayer`; `FeedCoordinator` turns visibility into playback intent, prepares assets off-main with real cancellation (`asset.cancelLoading()` on task cancel, since task cancellation alone does not stop an in-flight load), loops by seek-to-zero, and tears down in the order the `PlayerRenderTarget` rule requires. Verified on simulator: `occupancy 0, free 1` after every release — one player serves the whole session — and a 20-swipe fast scroll prepared **nothing** in between, only the departure and arrival indices acquiring. 25 tests / 38 cases, lint clean.
* **Decision**: **Playback intent fires on scroll settle, not continuously** ([decisions](decisions.md)). Continuous intent would acquire and release at every rounding boundary during a drag — thrashing the pool in exactly the fast-scroll case under study — and would make time-to-first-frame's `t0` ambiguous. All three settle events must be handled or playback silently fails to start for pages that came to rest that way.
* **Correction**: **`playerWaitDuration` was measuring the wrong thing.** The first implementation timed the whole acquire, so instantiating an `AVPlayer` (~5 ms, visible in the very first log line) was reported as contention. That would have penalised `pool-unbounded`, which instantiates on nearly every acquire and exists specifically to look *good* on startup and bad on memory — the metric would have quietly contradicted the finding it supports. Now zero unless genuinely blocked, with two regression tests using a clock that ticks on every read. [QoE metrics](qoe-metrics.md) updated to state the exclusion.
* **Decision**: Audio session set explicitly to `.playback`/`.moviePlayback`. The default `.soloAmbient` is silenced by the ringer switch, and a silenced session can mean the audio decode path does no work — so the same arm could measure a video-only pipeline on a muted device and a full one otherwise.
* **Correction**: The earlier claim that "four preloaded players at the system default is a memory problem" was an **inference from a duration, not a measurement** — 908 s buffered says nothing about bytes resident, since HLS segments could have been disk-backed. Probed directly (macOS, `phys_footprint`, four attached-but-unplayed items): system default **+90.9 MB**, capped at 5 s **+1.5 MB**. The inference held and the lever works, but it is now measured rather than assumed. Directional only — macOS, single run; the device measurement is now an explicit M4 acceptance item.
* **Decision**: **Buffer caps must be expressed in segment multiples.** `preferredForwardBufferDuration` cannot go below one segment: capping at 5 s yielded ~10 s per item because BipBop segments are ~10 s (`#EXT-X-TARGETDURATION:11`). The "e.g. 2–4 s" figure [playback engine](playback-engine.md) previously carried for `PreloadNext3Capped` would have been a **no-op on this corpus** — the arm would have appeared to test a capped buffer while testing only preload depth, and its comparison against `PreloadNext1` would have been silently confounded. Spec and code comment corrected.
* **Update**: M2 underway. `PlayerProviding`/`PlayerItemProviding` wrappers with AVFoundation adapters, and `PlayerPool` as an actor — fixed capacity, FIFO waiters, measured wait duration, cancellable acquire, three-way teardown, `drain()`, and an `unbounded` mode for the negative-control arm. 10 pool tests (13 cases) run against fakes and a fake clock: no device, no stream, and no real time elapsed. Suite now 23 tests / 36 cases, lint clean, all three configurations building.
* **Update**: **Two-tier preparation verified empirically** (macOS, Apple BipBop; throwaway script, not a committed test). An unattached `AVPlayerItem` never buffers — `status` stays `.unknown`, `loadedTimeRanges` stays empty after 8 s — so `poolCapacity ≥ |itemsToPrepare|` holds. Two findings beyond the question asked: **`play()` is not required to buffer**, attachment alone starts it, so preload means attach-and-stay-paused rather than play-muted-offscreen; and **the system default forward buffer is enormous** — ~908 s buffered to `isPlaybackBufferFull` from one paused item within six seconds, which makes `preferredForwardBufferDuration` capping the precondition for deep preload rather than a tuning nicety. Magnitude is macOS-specific and gets re-measured on device. See [playback engine](playback-engine.md) and [learning notes](ios-learning-notes.md).
* **Decision**: Three entries in [decisions](decisions.md) — `acquire()` throws so a blocked wait is cancellable (an unresumed continuation would leak during exactly the fast-scroll pattern under study); teardown responsibility split three ways across pool, cell, and instrumentation, with the table in [playback engine](playback-engine.md); domain enums mirror AVFoundation rather than re-exporting it, keeping the framework out of the protocols and out of the event vocabulary `Metrics/` consumes.

## 2026-08-01

* **Decision**: **No app-wide presentation architecture and no Combine** — both recorded in [decisions](decisions.md). MVVM/VIPER/TCA solve view-state problems this app does not have (four screens, one navigation edge, a feed whose presentation state is a single index); the hard state is domain state, and `MetricsEngine` is already a reducer, so TCA's determinism argument is satisfied without the dependency. Combine is declined because the deciding constraint is timestamp fidelity rather than ergonomics, and once the clock is read inside the callback the delivery mechanism is free — leaving Swift 6 `Sendable` friction, a second cancellation model alongside `Task`, and a hidden observation surface as its remaining costs. Small `@Observable` types are still used at the dashboard, HUD, and debug menu.
* **Decision**: Added a **measurement-discipline** section to [QoE metrics](qoe-metrics.md): the clock is read synchronously at the observation callback, before any queue or actor hop, using a monotonic source. Taking the timestamp where an event is *consumed* would fold delivery jitter into every interval and make arms differ for reasons unrelated to preload strategy. Also recorded in [observability](observability.md): the HUD **samples** aggregate state at 4 Hz rather than throttling a push stream, so a stall storm cannot turn the HUD into a load source.
* **Update**: **M1 complete.** Debug menu skeleton added — content summary, a per-source Credits screen (closing the attribution surface required by [content sources](content-sources.md)), and build configuration with an "unoptimized, not publishable" warning; reachable by on-screen button or shake. It carries only controls whose subsystem exists, so there are no inert placeholders to mistake for broken ones.
* **Decision**: **Three build configurations** — `Debug` (tools, unoptimized), `Measure` (tools, optimized), `Release` (no tools, optimized). Measuring TTFF or memory against an unoptimized binary would describe the build settings rather than the design, but a plain Release build has no way to drive a run protocol; the two concerns are independent axes. Gating is on `FEEDLAB_TOOLS` rather than `DEBUG`, verified by symbol count (debug menu present in `Measure`, absent from `Release`). [testing](testing.md) now requires `Measure` for every published number. See [decisions](decisions.md).
* **Decision**: Resolved the two structural questions [playback engine](playback-engine.md) had deferred. **Preparation is two-tiered** — asset load and `AVPlayerItem` construction need no player, but an item does not *buffer* until associated with one, so real preload costs a pool slot and `poolCapacity ≥ |itemsToPrepare|`. The existing arm table already satisfies the rule. Flagged for empirical confirmation in M2 rather than treated as settled. **A pure `PreparationPlanner`** arbitrates strategy intent against capacity, keeping `PreloadStrategy` capacity-unaware and testable, and keeping `playerWaitDuration` a measure of genuine contention rather than of a misconfigured arm.
* **Update**: [Architecture](architecture.md) gained a "Patterns, and what each one buys" section naming the shapes in use and what each is for — previously the design was consistent but nowhere described in those terms. The idea it foregrounds: cells recycle on scroll geometry, players recycle on playback intent, and keeping those two reuse pools decoupled is what makes pool capacity an experiment variable at all.
* **Update**: M1 substantially complete — only the debug-menu skeleton remains. Xcode project generated from an XcodeGen `project.yml` (Swift 6, iOS 17+, SwiftLint clean, folder structure per [architecture](architecture.md)); `Content/` layer with manifest decoding and licensing validation; `short-form.json` populated with 22 verified items; vertical paging `UICollectionView` with full-screen placeholder cells. 13 tests (24 cases) pass. Paging verified on simulator: pages land flush with no cumulative drift over 26 swipes.
* **Decision**: Four choices logged in [decisions](decisions.md) — XcodeGen `project.yml` as source of truth with the generated `.xcodeproj` committed; **Swift Testing instead of XCTest** (supersedes the XCTest reference in [testing](testing.md), since the suite is overwhelmingly table-shaped); Info.plist written explicitly rather than generated; manifest validation rejects non-HTTPS urls and derives stream format from the URL rather than a declared field.
* **Update**: [Content sources](content-sources.md) rewritten around what is *actually* reachable. Every URL was probed before commit. Most tutorial-famous sources are dead — `download.blender.org`, the Google `gtv-videos-bucket` MP4s, and Bitmovin's Sintel all 403; Wikimedia's Big Buck Bunny is VP9, which `AVPlayer` cannot decode. Consequence: licensable HLS is scarce, so `short-form.json` is 7 HLS + 15 NASA progressive, ABR metrics are valid only over `Manifest.hlsItems`, and this is recorded as a stated limitation rather than quietly absorbed.
