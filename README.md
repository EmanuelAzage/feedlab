# FeedLab

A vertical, full-screen video feed for iOS that **measures its own playback quality**.

A bounded pool of recycled `AVPlayer`s, swappable preload strategies behind an experiment harness, and a QoE instrumentation layer that reports time-to-first-frame, rebuffer ratio, bitrate behavior, and peak memory — live in a HUD while you scroll, and afterward in a Swift Charts dashboard.

> **Status:** in active development — see [docs/build-plan.md](docs/build-plan.md) for milestone progress.

## Why this exists

Playing one video is easy. Playing the *next* video instantly, on a phone, over a bad network, without the memory and decoder cost of a dozen live players, is the actual problem — and it's a problem you can only reason about with numbers. FeedLab is the rig I built to get those numbers.

Two things it's deliberately not: it's not a social app (no accounts, no backend, no likes), and it's not a wrapper around `AVPlayerViewController`. The feed cells own `AVPlayerLayer`s and the pooling is hand-rolled, because that surface is the thing being studied. Design rationale is logged in [docs/decisions.md](docs/decisions.md); what I learned along the way is in [docs/ios-learning-notes.md](docs/ios-learning-notes.md).

## The arms

| Arm | Preload | Pool | Hypothesis |
|---|---|---|---|
| `baseline` | none | 3 | Control. Worst-case startup, lowest memory. |
| `preload1` | next 1 | 3 | One-ahead preparation should cut startup for modest cost. |
| `preload3-capped` | next 3, capped buffers | 4 | Depth helps fast scrollers; capping should contain the memory cost. |
| `preload3-uncapped` | next 3, default buffers | 4 | Negative control isolating **the cap** — same depth, same pool. |
| `window` | prev 1 + next 2 | 4 | Preparing backward should help back-scroll, and costs a slot. |
| `pool-unbounded` | next 1 | ∞ | Negative control. Should look fine on startup and bad on memory. |

Two arms exist to lose. A rig that only tests good ideas proves nothing.

## How the numbers were produced

Every figure here comes from `Scripts/results_table.py` reading raw session records committed under
[`measurements/`](measurements/). Nothing is transcribed, and nothing is estimated: a metric that
hasn't been measured on device is left blank rather than filled in.

- **Device.** iPhone 12 Pro, iOS 26.5.2, `Measure` configuration — optimized, with instrumentation
  compiled in. Simulator numbers are never published; decode, memory accounting and thermal behaviour
  all differ.
- **The run script is code.** A UI test target drives 6 items forward, 6 back, twice round, at a
  fixed 5 s dwell, verifying that each flick actually paged. It is not a person swiping. An earlier
  hand-driven attempt drifted to 8 s median dwell against a 3 s target, and dwell is the denominator
  of rebuffer ratio — operator fatigue across a batch reads exactly like an arm effect.
- **≥3 runs per arm per network profile**, arms alternated rather than run consecutively so thermal
  drift and cache warmth spread across them. Median of runs reported, with the observed range.
- **Cold start per run**; the first item view is discarded as a warm-up.

### Limits, stated rather than buried

- **The corpus is 7 HLS streams, and that is the whole measurement corpus.** Publicly available HLS
  whose content licensing can actually be named is scarce. The app's default feed is 22 items, but
  15 of those are progressive MP4 — and **27% of progressive item views on this device rendered a
  first frame and then never played** (0% of HLS). Those views scored a good startup time, zero
  stalls and a 0.000 rebuffer ratio, because a stall can only be counted after playback begins. They
  would move p90 startup more than any preload strategy does, so the comparison excludes them. The
  metric that caught it is still implemented and still reported.
- **Only the first lap is cold.** Lapping a 7-item corpus is what makes a per-run p90 a real
  percentile (22 samples rather than 7) instead of the worst single item. The cost is that later
  views hit a warm CDN and OS cache, which compresses the differences between arms — equally for
  every arm, so the ranking holds, but the magnitudes are a **floor** on what a cold audience would
  see, not an estimate of it.
- **The measurement harness is not free.** Driving the run from XCUITest enables accessibility in the
  app process and raised peak footprint by ~1.9 MB against a hand-driven run. Constant across arms,
  so comparisons hold — but these memory figures are not comparable to a non-instrumented build.
- **Not an A/B test.** Single device, single operator, manually selected arms, n=1 user.
  Randomization would add variance without adding validity. The harness is *structured* like an
  online experiment — named arms, per-arm records, aggregate comparison — so the methodology
  transfers, but the results are a measurement rig's, not an experiment platform's.
- **Peak memory is peak *observed*.** Sampled at 5 Hz; a spike between samples is invisible, so the
  figure is a lower bound.

Full methodology in [docs/experiment-harness.md](docs/experiment-harness.md) and
[docs/testing.md](docs/testing.md); metric definitions in [docs/qoe-metrics.md](docs/qoe-metrics.md).

## How it works

```
Feed UI (UICollectionView paging · FeedCell owns AVPlayerLayer)
        │
FeedCoordinator — visibility → playback intent
        │
PlaybackEngine ── PlayerPool (bounded, recycled)
                └ PreloadStrategy (from the active experiment arm)
        │
Instrumentation — typed PlaybackEvents (KVO, notifications, access/error logs)
        │
Metrics (pure, no AVFoundation) — fold events → PlaybackRecord → SessionSummary
        │
HUD · Swift Charts dashboard · CSV/JSON export · os_signpost
```

The boundary that matters: **AVFoundation lives only in the playback and instrumentation layers.** Metric computation is a pure fold over typed events with injected timestamps, so stall detection, TTFF, and aggregation are unit-tested against synthetic edge cases without a device or a live stream. See [docs/architecture.md](docs/architecture.md) and [docs/testing.md](docs/testing.md).

Metric definitions — what counts as a stall, when the TTFF clock starts, why aggregate rebuffer ratio isn't the mean of per-item ratios — are specified in [docs/qoe-metrics.md](docs/qoe-metrics.md).

## Running it

Requirements: Xcode 16+, iOS 17+ device (the simulator misreports decode and memory — see below).

```bash
git clone <repo> && cd FeedLab
open FeedLab.xcodeproj
```

### Reproducing a measurement run

The run protocol is a UI test target, so it is reproducible rather than described:

```bash
TEST_RUNNER_FEEDLAB_ARM=preload1 \
xcodebuild test -scheme FeedLabRunner -configuration Measure \
  -destination 'platform=iOS,id=<device ECID>'

# pull the sessions it wrote, then regenerate the table
xcrun devicectl device copy from --device <device UUID> \
  --domain-type appDataContainer --domain-identifier dev.emanuelazage.FeedLab \
  --user mobile --source 'Library/Application Support/FeedLab/Sessions' --destination ./out
Scripts/results_table.py ./out --profile "unthrottled Wi-Fi"
```

Only the arm is required — it has no default, because a run mislabelled as the control is worse than
one that refuses to start. Set Auto-Lock to Never first; a locked device leaves `xcodebuild` waiting
indefinitely rather than failing.

No API keys, no backend, no setup. Video comes from a manifest of public test streams. The project is
generated from `project.yml` with [XcodeGen](https://github.com/yonaskolb/XcodeGen); the `.xcodeproj` is
committed, so you only need XcodeGen if you change the project structure (`xcodegen generate`).

Three build configurations, because debug tooling and representative performance are independent axes:

| Configuration | Tooling | Optimized | Use |
|---|---|---|---|
| `Debug` | yes | no | development |
| `Measure` | yes | **yes** | measurement runs — the only source of published numbers |
| `Release` | no | yes | the clean app |

Debug menu (shake or the on-screen button) selects the experiment arm, toggles the HUD, and opens the dashboard. It reports the active configuration and warns when the build is unoptimized, so a run against the wrong binary can't happen quietly.

**On the simulator:** the app runs, but any number it produces is meaningless. Decode is software, memory accounting differs, and there's no thermal behavior. All published figures come from a physical device under a stated network profile.
